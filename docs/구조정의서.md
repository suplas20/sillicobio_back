# SillicoBio FastAPI 백엔드 API 구조 설계 문서

## 1. 문서 목적

본 문서는 SillicoBio 발효 실험 관리 시스템의 백엔드 API 개발을 위한 기본 구조를 정리한 문서이다.

백엔드는 **Python FastAPI** 기반으로 개발하며, 데이터베이스는 **PostgreSQL**을 사용한다.
ORM은 **SQLAlchemy 2.x**, 마이그레이션 관리는 **Alembic**을 기준으로 한다.

본 구조는 다음 기능을 안정적으로 확장할 수 있도록 설계한다.

* 로그인
* 회원 관리
* 연구자 관리
* 실험 등록
* 배치 등록
* 배치 데이터 등록
* 결과 조회
* 첨부파일 관리
* 계산식 처리
* PostgreSQL 연동

## 4.3 `app/db/`

PostgreSQL 연결과 SQLAlchemy 세션을 관리한다.

```text
db/
├── database.py
└── session.py
```

### `database.py`

SQLAlchemy 엔진과 Base 클래스를 정의한다.

예시:

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase

DATABASE_URL = "postgresql+psycopg://user:password@localhost:5432/sillicobio"

engine = create_engine(DATABASE_URL)

class Base(DeclarativeBase):
    pass
```

### `session.py`

API에서 사용할 DB 세션을 생성한다.

예시:

```python
from sqlalchemy.orm import sessionmaker
from app.db.database import engine

SessionLocal = sessionmaker(
    autocommit=False,
    autoflush=False,
    bind=engine
)

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

## 4.4 `app/models/`

DB 테이블과 매핑되는 SQLAlchemy 모델을 관리한다.

```text
models/
├── member.py
├── researcher.py
├── experiment.py
├── batch.py
├── batch_data.py
└── attachment.py
```

모델은 실제 PostgreSQL 테이블 구조와 연결된다.

예시:

```python
from sqlalchemy import String, Boolean
from sqlalchemy.orm import Mapped, mapped_column
from app.db.database import Base

class TbMember(Base):
    __tablename__ = "tb_member"

    member_id: Mapped[int] = mapped_column(primary_key=True, index=True)
    login_id: Mapped[str] = mapped_column(String(50), unique=True, nullable=False)
    password_hash: Mapped[str] = mapped_column(String(255), nullable=False)
    member_name: Mapped[str] = mapped_column(String(100), nullable=False)
    role: Mapped[str] = mapped_column(String(20), nullable=False)
    is_active: Mapped[bool] = mapped_column(Boolean, default=True)
```

주의사항:

* PostgreSQL 테이블명은 모두 소문자로 구성한다.
* 모델의 `__tablename__`도 실제 테이블명과 동일하게 소문자로 작성한다.
* DB 컬럼명과 모델 필드명은 가능한 동일하게 유지한다.

## 4.5 `app/schemas/`

API 요청 및 응답 데이터 형식을 정의한다.

FastAPI에서는 Pydantic 모델을 사용한다.

```text
schemas/
├── member_schema.py
├── researcher_schema.py
├── experiment_schema.py
├── batch_schema.py
├── batch_data_schema.py
└── attachment_schema.py
```

역할은 다음과 같다.

* API 요청 데이터 검증
* API 응답 데이터 구조 정의
* DB 모델과 외부 API 구조 분리

예시:

```python
from pydantic import BaseModel

class MemberCreate(BaseModel):
    login_id: str
    password: str
    member_name: str
    role: str

class MemberResponse(BaseModel):
    member_id: int
    login_id: str
    member_name: str
    role: str
    is_active: bool

    class Config:
        from_attributes = True
```

모델과 스키마는 반드시 분리한다.

```text
models  = DB 테이블 구조
schemas = API 요청/응답 구조
```

## 4.8 `app/api/v1/`

API 버전별 라우터를 관리한다.

```text
api/
└── v1/
    ├── router.py
    └── endpoints/
        ├── auth.py
        ├── members.py
        ├── researchers.py
        ├── experiments.py
        ├── batches.py
        ├── batch_data.py
        ├── results.py
        └── attachments.py
```

### `router.py`

각 API endpoint 파일을 하나로 묶는다.

예시:

```python
from fastapi import APIRouter
from app.api.v1.endpoints import (
    auth,
    members,
    researchers,
    experiments,
    batches,
    batch_data,
    results,
    attachments
)

api_router = APIRouter()

api_router.include_router(auth.router, prefix="/auth", tags=["Auth"])
api_router.include_router(members.router, prefix="/members", tags=["Members"])
api_router.include_router(researchers.router, prefix="/researchers", tags=["Researchers"])
api_router.include_router(experiments.router, prefix="/experiments", tags=["Experiments"])
api_router.include_router(batches.router, prefix="/batches", tags=["Batches"])
api_router.include_router(batch_data.router, prefix="/batch-data", tags=["Batch Data"])
api_router.include_router(results.router, prefix="/results", tags=["Results"])
api_router.include_router(attachments.router, prefix="/attachments", tags=["Attachments"])
```

### `endpoints/`

실제 API 주소를 정의한다.

예시:

```python
from fastapi import APIRouter, Depends
from sqlalchemy.orm import Session
from app.db.session import get_db

router = APIRouter()

@router.get("/")
def get_experiments(db: Session = Depends(get_db)):
    return {
        "message": "실험 목록 조회"
    }
```

Endpoint 파일은 요청을 받고 응답을 반환하는 역할에 집중한다.
실제 업무 로직은 service로 위임한다.

## 6. 기능별 API 설계

## 6.1 로그인 API

```text
POST /api/v1/auth/login
POST /api/v1/auth/logout
GET  /api/v1/auth/me
```

### 로그인 처리 방식

이번 프로젝트는 토큰 인증을 사용하지 않는다.
로그인 시 DB에 저장된 사용자 정보를 조회하고, 입력된 비밀번호와 저장된 비밀번호를 비교한다.

기본 흐름:

```text
1. 사용자가 ID/PW 입력
2. 백엔드에서 login_id로 사용자 조회
3. 비밀번호 검증
4. 일치하면 사용자 정보 반환
5. 프론트엔드에서 로그인 상태 관리
```

## 7. API 처리 흐름

API 요청은 다음 흐름으로 처리한다.

```text
Frontend
  ↓
Endpoint
  ↓
Service
  ↓
CRUD
  ↓
Model
  ↓
PostgreSQL
```

예를 들어 실험 등록 API의 처리 흐름은 다음과 같다.

```text
1. 프론트엔드에서 실험 등록 요청
2. endpoints/experiments.py에서 요청 수신
3. experiment_service.py에서 업무 로직 처리
4. experiment_crud.py에서 DB 저장
5. models/experiment.py를 통해 PostgreSQL 테이블과 매핑
6. 처리 결과 반환
```

## 8. 계층별 책임

| 계층       | 역할                      |
| -------- | ----------------------- |
| Endpoint | API 주소 정의, 요청 수신, 응답 반환 |
| Service  | 업무 로직 처리, 권한 확인, 계산식 처리 |
| CRUD     | DB 조회, 등록, 수정, 삭제       |
| Model    | DB 테이블 구조 정의            |
| Schema   | API 요청/응답 데이터 구조 정의     |
| DB       | PostgreSQL 데이터 저장       |

---

## 9. 설계 원칙

## 9.1 Endpoint에 모든 로직을 넣지 않는다

좋지 않은 구조:

```text
endpoints/experiments.py 안에서
DB 조회
권한 확인
계산
저장
응답 생성
전부 처리
```

권장 구조:

```text
Endpoint → Service → CRUD → Model → DB
```

---

## 9.2 Model과 Schema를 분리한다

```text
Model  = DB 테이블 구조
Schema = API 요청/응답 구조
```

분리하는 이유는 다음과 같다.

* DB 구조와 API 응답 구조가 항상 같지 않다.
* 비밀번호 같은 민감 정보는 응답에서 제외해야 한다.
* API 요청용, 응답용, 수정용 데이터를 다르게 정의할 수 있다.
* 유지보수가 쉬워진다.

---

## 9.3 API 버전을 붙인다

모든 API는 `/api/v1`으로 시작한다.

```text
/api/v1/experiments
/api/v1/batches
/api/v1/results
```

나중에 구조가 크게 변경되면 `/api/v2`를 추가할 수 있다.

---

## 9.4 계산식은 Service로 분리한다

계산식은 API 파일이나 CRUD 파일에 직접 넣지 않는다.

계산식은 다음 파일에서 관리한다.

```text
services/calculation_service.py
```

계산식 분리 이유:

* 계산식 변경 시 한 파일만 수정 가능
* 화면 계산과 백엔드 검증 로직을 분리 관리 가능
* 테스트 코드 작성이 쉬움
* 결과 산출 로직 확장 가능

---

## 9.5 DB 테이블명은 소문자로 통일한다

PostgreSQL에서는 테이블명을 소문자로 통일하는 것이 관리하기 쉽다.

예시:

```text
tb_member
tb_researcher
tb_experiment
tb_batch
tb_batch_data
tb_attachment
```

SQLAlchemy 모델에서도 동일하게 작성한다.

```python
__tablename__ = "tb_member"
```

## 14. 최종 요약

SillicoBio FastAPI 백엔드는 다음 구조를 기준으로 개발한다.

```text
Endpoint
→ Service
→ CRUD
→ Model
→ PostgreSQL
```

핵심 원칙은 다음과 같다.

* API는 `/api/v1` 기준으로 구성한다.
* DB 테이블명은 모두 소문자로 작성한다.
* Model과 Schema를 분리한다.
* Endpoint에는 복잡한 업무 로직을 넣지 않는다.
* 계산식은 Service 계층으로 분리한다.
* PostgreSQL 연동은 SQLAlchemy 2.x와 psycopg를 사용한다.
* DB 변경 관리는 Alembic으로 처리한다.
* 로그인은 토큰 방식이 아닌 DB 사용자 정보 비교 방식으로 시작한다.

이 구조는 초기 개발이 쉽고, 이후 실험 데이터 증가, 배치 데이터 확장, 결과 차트 기능 추가에도 대응하기 좋은 구조이다.
